# BROWN SWARM — сквозная нумерация контрактов и возвраты F

**Статус:** УТВЕРЖДЕНО владельцем, уточнение от 2026-11-23.
**Применение:** публичный каталог `player5/ContractsPolivas` и резчики/Producer BROWN COMMAND.

## Формат

`<TYPE><NNN>D<DEPENDENCY><SERIES>[F]`

| Поле | Значение |
|---|---|
| `TYPE` | `C` — основной исполнительский контракт; `V` — независимый Validator; `I` — интеграция у уполномоченного Producer/Integrator (не выдавать внешнему worker без права) |
| `NNN` | **Сквозной** трёхзначный порядковый номер; общий для разных типов, не начинается с 001 для каждого типа |
| `D000` | Нет зависимости от другого контракта |
| `D003` | Зависимость от контракта с порядковым №003, точный `depends_on` указывается в карточке |
| `SERIES` | Например `TST` — тестовая серия, не отдельный исполнитель |
| `F` **в самом конце** | Возврат на исправление **по замечанию Validator до интеграции**, приоритетно относительно обычных готовых задач, **но после всех необходимых зависимостей** |

**Пример:** `C003D000TST` — третий номер, основной контракт без блокера; `V004D003TST` — четвёртый номер, Validator зависит от `C003D000TST`. Если Validator установил дефект и до интеграции потребовал исправить C003, маркировка возврата — `C003D000TSTF`, **а не** `F005D003TST` и **не** новый порядковый номер. Суффикс `F` сам по себе не отменяет проверок/зависимостей.

## Очередь и приоритеты

1. Producer/Cutter **резервирует очередной свободный сквозной NNN** после проверки действующего индекса, истории и реестра. Dispatcher только читает опубликованный индекс и сам новых номеров не назначает.
2. Сначала выполняются только задания с удовлетворёнными зависимостями / GATE. **Приоритет возврата с конечной F** применяется **только внутри множества готовых к выдаче** задач; F не может перепрыгнуть невыполненный D###
3. При `VALIDATION=FAIL / NEEDS_FIX` сохраняется исходный контракт и его история. Для возврата фиксируются основание, конкретные замечания, source SHA, iteration/attempt/revision и признак `F` в конце. Нельзя выдавать новую бесконтрольную попытку под тем же delivery ID.
4. Обычная повторная транспортная отправка (`DISPATCH-...`, `PUBLISH-...`) **не** резервирует новый NNN, **не** создаёт новый контракт и не является отдельной итерацией/попыткой.
5. `I1-A3` обозначает `iteration=1, attempt=3` в конкретном задании. Эти числа не равны `NNN`.
6. После подтверждённой публикации ответа/результата уполномоченный Publisher/Producer переводит контракт в `PROCESSED / RESULT_PUBLISHED`, убирает строку из активного индекса, сохраняет карточку/историю и только затем активирует зависимый Validator. Статус `DONE` Worker, клик Send или ожидание 120 секунд **не** подтверждают публикацию.
7. После проверенного результата Validator уполномоченная сторона переводит V в `PROCESSED` либо `NEEDS_FIX`, при необходимости ставит приоритетное `F` в очередь. Удалять карточки не требуется.

## Технический статус

**PARTIAL / NOT IMPLEMENTED IN DISPATCHER FIX12P4:** парсер понимает ID как строки и зависимости по `depends_on`, но не содержит полноценного резерватора сквозных номеров, автоматической приоритетной очереди по конечной `F`, перехода PROCESSED по фактическому SHA readback и чтения внешнего Publisher-промпта. Это требования к следующей транспортной доработке, а не доказательство работы нынешнего EXE.

**Существующие номера 001 и 002 сохраняются как исторические.** Новые тесты: `C003D000TST`, `V004D003TST`. Нельзя задним числом переименовывать старые доставленные задания.
