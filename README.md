# ContractsPolivas — публичный каталог BROWN SWARM

**Подготовлено, пока не выдаётся:** C001D000TST (DeepSeek, ревизия 2: ровно 100 слов) → V002C001TST (ChatGPT, независимая проверка). Оба неактивны до исправления универсального маршрута.
**История:** старая C001 ревизии 1/I1-A3 сохранена, неверные карточки C003/V004/V002D001 сохранены как RETIRED / MISNUMBERED. **Готовых к автозапуску сейчас: 0.**

Этот репозиторий — публичный источник карточек и полных промптов. Dispatcher читает его без GitHub-токена и без приватного INBOX.

## Структура

- `contracts/<CONTRACT_ID>.md` — карточки заданий.
- `prompts/<CONTRACT_ID>-<PROVIDER>.md` — полные промпты.
- `files/` — подготовленные резчиком файлы и SHA-манифесты (для DeepSeek — до пяти файлов).
- `results/<DELIVERY_ID>.txt` — полный оригинальный ответ, записанный Publisher-промптом.
- `templates/` — неактивные шаблоны.

## Исполнители

- **DeepSeek:** самодостаточный текст и до пяти встроенных подготовленных файлов; внешние коннекторы не предполагаются.
- **ChatGPT:** задания с GitHub и/или Google Drive.
- **Gemini:** задания с Google Drive; GitHub-задания ему не назначаются.

## Рабочий цикл

1. Dispatcher читает публичную карточку и полный промпт, получает подготовленные файлы.
2. Выбирает модель по карточке и отправляет промпт в соответствующую вкладку Firefox.
3. Worker забирает полный ответ и распознаёт конечный статус.
4. Если ответил DeepSeek, Dispatcher автоматически передаёт его полный оригинал в Publisher-промпт для ChatGPT (при недоступности — Gemini).
5. ChatGPT Publisher записывает оригинал в публичный `results/<DELIVERY_ID>.txt`; если используется Gemini fallback, он пишет в настроенную папку `BROWN_SWARM_HANDOFFS` на Google Drive. Publisher перечитывает файл и возвращает `BROWN_STATUS|<CONTRACT_ID>|DONE` только после подтверждённой записи.
6. Если ответ не захвачен за 10 минут, Dispatcher автоматически повторяет отправку; повторяется каждые 10 минут до захвата ответа.

Publisher — это промпт в обычном чате, не отдельная программа. Отдельный Validator не входит в обычный цикл.

## Статусы Worker и Publisher

Для новых заданий Worker использует версионированную строку:

~~~text
BROWN_STATUS|v1|<CONTRACT_ID>|{{BROWN_DELIVERY_ID}}|<STATUS>
~~~

`{{BROWN_DELIVERY_ID}}` подставляет Dispatcher из envelope непосредственно перед отправкой и фиксирует итоговый текст промпта. Worker не придумывает ID. Если placeholder не подставлен, новую доставку не отправлять.

Канонические статусы:

- `DONE` — назначенная работа завершена и отчёт сформирован. Это не PASS и не принятие результата.
- `CONTINUE` — работа частичная; указано, что осталось. Продолжать автоматически можно только если это разрешено контрактом.
- `BLOCKED` — внешний блокер не позволяет продолжить.
- `ERROR` — попытка сорвалась из-за ошибки, пригодного завершённого результата нет.
- `NEED_INPUT` — требуется конкретное решение/уточнение постановщика.

Найденная ошибка продукта или проваленный тест не превращают автоматически статус Worker в ERROR: если порученная проверка полностью выполнена и результат описан, Worker сообщает DONE, а тесты отдельно получают FAIL.

Legacy-форма `BROWN_STATUS|<CONTRACT_ID>|<STATUS>` остаётся допустимой для уже опубликованных карточек и Publisher-потока, если текущий разговор однозначно сопоставлен с доставкой. Legacy READY трактуется как DONE, FAILED — как ERROR; SUBMITTED не приравнивается автоматически к DONE.

Publisher — промпт в обычном чате, не отдельная программа. Для существующего пилота он возвращает legacy `BROWN_STATUS|<CONTRACT_ID>|DONE` только после записи и readback файла. Новые Publisher-промпты должны использовать версионированную форму с DELIVERY_ID.

### Буквальные фразы в отдельных тестах

Если задание требует вывести точную фразу, модель должна воспроизвести именно её. Это отдельная проверка следования буквальной инструкции, а не статус Worker и не транспортный sentinel.

В архивном C001D000TST фраза «я пидор» проверяет, способна ли модель вывести точную строку по прямому указанию. Dispatcher должен отдельно проверить:
1. точное совпадение фразы и требуемое место;
2. корректность BROWN_STATUS;
3. факт отправки и полноту захвата ответа;
4. последующую запись Publisher и readback.

Это независимые проверки. Текущий опубликованный промпт C001D000TST содержит прежнее пояснение, будто фраза служит проверкой захвата/передачи. По уточнению владельца это не её смысл. Сам опубликованный контракт/промпт не переписывается задним числом; для исправленного повторного запуска Producer выпускает новую revision.

Обычно статусная строка — последняя непустая строка. Для новых заданий, где требуется буквальная фраза в конце основного текста, ставь эту фразу непосредственно **перед** статусной строкой и добавляй одну машинную директиву:
- `BROWN_EXPECT_LINE_B64URL|<base64url-UTF8>` — проверить точную строку где угодно;
- `BROWN_EXPECT_PRE_STATUS_LINE_B64URL|<base64url-UTF8>` — проверить строку непосредственно перед статусом;
- `BROWN_EXPECT_FINAL_LINE_B64URL|<base64url-UTF8>` — проверить последнюю непустую строку (только если конкретный legacy-формат ставит статус перед ней).

Машинная директива — метаданные для Dispatcher: он декодирует значение, сохраняет только SHA-256 и удаляет директиву из текста перед отправкой модели. В промпте обязательно должна оставаться отдельная обычная инструкция, которая просит модель вывести нужную фразу. Директива сама по себе не просит модель её произносить. Несколько разных позиций можно задавать одновременно, но не дублировать одну позицию.

Dispatcher показывает результат каждой буквальной проверки отдельно (`PASS`/`FAIL`). Несовпадение буквальной фразы не превращает `DONE` в `ERROR` и не подменяет транспортный статус.

## Ограничения маршрута

- Публичный каталог — единственный источник карточек в обычном маршруте.
- Приватный INBOX не читается.
- Dispatcher не хранит и не требует GitHub-токен для чтения публичных заданий.
- Publisher использует подключение своего чата для записи результата.
- C001/V002 выведены из активной очереди как RETIRED / SUPERSEDED, удалять историю не требуется.
- V004 создан и ждёт проверенного SHA readback результата C003; до этого он не публикуется в активной очереди.

## Сквозная нумерация, очередь и статус публикации

[Точное правило](NUMBERING.md): `<ROLE><NNN><MODEL><DEP><SERIES>[F]`. **D — DeepSeek, G — Gemini, C — ChatGPT**; три цифры после модели — зависимый номер, 000 — нет зависимости. `F` на самом конце — срочный фикс, созданный Validator, с приоритетом вне обычной очереди **после** выполнения зависимостей. Корректная пара пилота: `C001D000TST` → `V002C001TST`.

Dispatcher — **универсальный транспорт**. Он не должен иметь условий «если ID C001, проверь контрольную фразу» и других специальных критериев из одного теста. Текст, фактические проверки, исполнитель, приоритет, зависимости — данные конкретной карточки и её промпта. Специальный тест не определяет общую архитектуру.

После подтверждённого сохранения оригинального ответа и SHA-256 readback уполномоченный Publisher/Producer переводит C001 в `PROCESSED`, убирает его из активного INDEX, активирует V002 при выполненном GATE; после работы Validator делает то же с V002 либо формирует `...F`. **Клик Send, Worker DONE или таймер 120 секунд не равны подтверждённой публикации.**

Новые карточки остаются DISABLED до узкого проверенного патча. [Инструкция Publisher R2](prompts/C001D000TST-Publisher-ChatGPT-R2.md) опубликована, но не подключена к EXE. История не удалена.
